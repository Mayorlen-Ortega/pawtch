# Lost-to-Found Pet Matching for Coquimbo - Technical Spec

## How This Works, In Plain Language

The app has two local parts. Angular is the part the person sees in the browser: it displays the welcome screen, report forms, report details, possible-match cards, and the comparison view. A small Python service is the part that receives form data, saves reports and photos, compares reports, and sends structured results back to Angular.

Reports are saved in a readable JSON file, and uploaded photos are saved in a local images folder. When a found-pet report is submitted, Python compares its photo with the photos from lost-pet reports using a local CLIP model. CLIP turns each photo into a list of numbers called an embedding; photos with similar visual content have embeddings that point in similar directions. Python also calculates separate scores for physical characteristics, location, and dates. It combines those four scores using named weights, but returns each contribution so the interface can explain the result.

The POC does not need accounts, a hosted database, a cloud vision API, a background job, or Ollama. This shape keeps the interesting AI work inspectable while keeping the demo local and manageable.

## The Core Journey Through the System

1. The browser opens Angular's welcome screen. Angular renders the purpose message and the two report choices. Implements `prd.md > The Core Journey` and `prd.md > Screens and Layout`.
2. The person chooses `I lost a pet` or `I found a pet`. Angular opens the corresponding single-page form. Implements `prd.md > Reporting a lost or found pet`.
3. The person fills the Photo, About the pet, and Where and when sections. Angular validates required fields before sending anything. Invalid fields remain filled and display specific messages. Implements `prd.md > Validation and recovery`.
4. Angular sends the form and photo as a multipart HTTP request to the Python API. The API validates the request, saves the photo under `backend/data/images/`, and appends the report to `backend/data/reports.json`.
5. For a lost report, the API returns the saved report and its current matches. For a found report, the API loads existing lost reports, generates or loads the new photo embedding, calculates the four evidence signals, and saves the resulting match records.
6. Angular shows a simple success confirmation and navigates to the report detail page. The detail page asks the API for the report and possible matches. Implements `prd.md > Screens and Layout` and `prd.md > Submission success`.
7. If there is no compatible match, Angular renders `No possible matches yet` and explains that a future compatible found report may appear. If there is a match, Angular renders a calm `Possible match` card with the other photo, the similarity or match indication, and evidence contributions. Implements `prd.md > Possible-match discovery` and `prd.md > States and Boundaries`.
8. The person selects `Compare reports`. Angular requests the two reports and match evidence, then renders a side-by-side comparison on wide screens and a readable stacked comparison on narrow screens. Implements `prd.md > Comparing reports`.

## Stack

### Frontend: Angular and TypeScript

Angular with TypeScript provides the browser application, form handling, routing between the welcome, report, detail, and comparison surfaces, and responsive UI components. The learner already works comfortably with Angular and TypeScript, so this keeps the user-facing build familiar while giving the agent a clear structure to follow.

Documentation: [Angular documentation](https://angular.dev/), [TypeScript documentation](https://www.typescriptlang.org/docs/).

Use the Angular version generated by the installed CLI and record it in `package.json`; verify the current compatible Node.js version during setup rather than assuming a version from this document.

### Python API: FastAPI

FastAPI provides a small local HTTP API with JSON responses and multipart upload handling. It keeps the frontend/matching boundary explicit without requiring a production server architecture.

Documentation: [FastAPI documentation](https://fastapi.tiangolo.com/), [Uvicorn documentation](https://www.uvicorn.org/).

### Local image matching: CLIP through Transformers and PyTorch

Use a standard pretrained CLIP image model, initially `openai/clip-vit-base-patch32`, loaded locally through Hugging Face Transformers and PyTorch. The model is chosen for established tooling and a clear learning path. Its weights are downloaded on first setup and are not committed to Git. If this model proves impractical on the local machine, investigate a lightweight mobile-oriented CLIP model without changing the visible matching contract.

Documentation: [Transformers CLIP documentation](https://huggingface.co/docs/transformers/model_doc/clip), [PyTorch documentation](https://pytorch.org/docs/stable/index.html), [OpenAI CLIP model card](https://huggingface.co/openai/clip-vit-base-patch32).

### Local persistence: JSON and image files

Reports are stored in `backend/data/reports.json`; uploaded images are stored in `backend/data/images/`. This is intentionally not a concurrent production database. It is transparent, inspectable, and sufficient for a small local demo.

## Where It Runs and How Someone Tries It

The POC runs locally as two processes:

1. Install a supported Node.js version for the Angular CLI and a supported Python version. Verify the versions against the current Angular and PyTorch/Transformers setup during the first build step.
2. Start the Python API from `backend/`:

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m uvicorn app.main:app --reload --port 8000
```

3. In a second terminal, start Angular from `frontend/`:

```powershell
npm install
npm start -- --port 4200
```

4. Open `http://localhost:4200` for the demo. The API is available at `http://localhost:8000`; its interactive documentation is at `http://localhost:8000/docs`.
5. The first matching request may take longer while the local CLIP model loads. The demo should use a small set of reports and photos.

The required submission still needs a short demo video and a public GitHub repository. Deployment is optional and is not part of this POC plan. Local startup and recording are sufficient.

## Look and Feel

Implement `prd.md > Look and Feel` with a warm off-white or cream background, muted botanical green as the main accent, and soft blue as the secondary accent. Use a friendly, highly readable rounded sans-serif typeface without a childish tone. Use real pet photos as the primary visual content, softly rounded cards, generous spacing, clear hierarchy, and consistent rounded icons.

The interface should feel calm, humane, trustworthy, and connected subtly to Coquimbo's coastal/natural setting. Possible-match cards should use reassuring visual treatment rather than warning or error styling. Avoid neon gradients, glassmorphism, glowing effects, robot imagery, and generic AI-dashboard patterns. Keep the AI visually quiet: evidence should be legible, but the interface should feel like a community service.

## Components

### Angular application shell and routing

Owns the welcome route, report form routes, report detail route, and comparison route. Provides shared navigation and responsive page layout.

PRD ref: `prd.md > The Core Journey`; `prd.md > Screens and Layout`.

### Welcome surface

Explains the purpose and presents `I lost a pet` and `I found a pet`, with slightly stronger emphasis on the lost path while keeping both accessible.

PRD ref: `prd.md > Screens and Layout > Welcome screen`.

### Report form

Renders the shared three-section structure and switches field configuration for lost versus found reports. Handles local form values, required-field validation, photo selection, upload errors, and retry without clearing unrelated values.

PRD ref: `prd.md > Screens and Layout > Lost-pet report form`; `prd.md > Screens and Layout > Found-pet report form`; `prd.md > Validation and recovery`.

### Report detail surface

Loads one report and its possible matches. Renders the empty state or a prominent possible-match card. Shows a submission confirmation when entered after successful creation.

PRD ref: `prd.md > Screens and Layout > Report detail page`; `prd.md > Possible-match discovery`.

### Possible-match card

Shows the other pet's photo, a non-definitive similarity or match indication, and separate evidence summaries for visual, physical, geographic, and date signals. Uses calm language and never states that the animals are confirmed to be the same.

PRD ref: `prd.md > Possible-match discovery`; `prd.md > Look and Feel`.

### Comparison surface

Loads both reports and the match explanation. Renders comparable photos and fields side by side on wide screens and in a stacked but clearly paired layout on narrow screens.

PRD ref: `prd.md > Screens and Layout > Side-by-side comparison view`; `prd.md > Comparing reports`.

### Python API routes

Keep the API small:

- `GET /api/locations` returns the curated location choices and their fixed coordinates.
- `GET /api/reports` returns the small report collection for the POC.
- `POST /api/reports` accepts a multipart report payload and photo, saves the report, and calculates matches when the report type is `found`.
- `GET /api/reports/{report_id}` returns one report.
- `POST /api/reports/{report_id}/resolve` marks a report resolved while retaining its photo.
- `DELETE /api/reports/{report_id}` permanently removes a report, its photo, and related matches.
- `GET /api/reports/{report_id}/matches` returns possible matches for that report.
- `GET /api/matches/{match_id}` returns both report summaries and the full evidence breakdown for comparison.
- `GET /media/{filename}` serves a saved local report image.

The API returns validation errors as structured field messages so Angular can preserve values and highlight only the affected fields.

PRD ref: `prd.md > Reporting a lost or found pet`; `prd.md > Validation and recovery`; `prd.md > Possible-match discovery`; `prd.md > Comparing reports`.

### Storage service

Reads and writes `reports.json` and the local images folder. Resolving updates the report status and timestamp but preserves its photo; match queries ignore resolved reports. Permanent deletion removes the report, its image, and related match records. Writes should be simple and safe for this single-user POC: load the current JSON, update it, and write it back. The service creates empty data files and folders on first run if they do not exist. Legacy reports without a status are treated as active.

PRD ref: `prd.md > States and Boundaries > Sample data`; `prd.md > Deferred From the POC`.

### Matching service

Loads the CLIP model once when needed, creates normalized image embeddings, calculates the four evidence signals, applies the named weights, and returns both the combined indication and individual contributions.

PRD ref: `prd.md > Possible-match discovery`; `prd.md > Product Decisions`.

## Data Model

### Report

```json
{
  "id": "report-001",
  "type": "lost",
  "status": "active",
  "photo": "report-001.jpg",
  "species": "dog",
  "color": "brown and white",
  "markings": "white chest and dark patch over left eye",
  "name": "optional for lost reports",
  "sex": "optional",
  "size": "optional",
  "description": "optional",
  "locationId": "coquimbo-centro",
  "date": "2026-09-20",
  "createdAt": "2026-09-25T12:00:00Z",
  "resolvedAt": null
}
```

`status` is `active` or `resolved`; `resolvedAt` is set when the report is resolved. Required values are `type`, `photo`, `species`, `color`, `markings`, `locationId`, and `date`. `name`, `sex`, `size`, and `description` are optional for lost reports; `name` and `sex` are not collected for found reports in the POC.

### Location

Locations are curated records such as recognizable Coquimbo-area sectors or communes. Each has an `id`, display name, latitude, and longitude. The authoritative list lives in a small backend data file or constant and is returned by `GET /api/locations`.

### Match

```json
{
  "id": "match-001",
  "lostReportId": "report-001",
  "foundReportId": "report-002",
  "visualScore": 82,
  "physicalScore": 75,
  "geographicScore": 90,
  "dateScore": 100,
  "weightedIndication": 82,
  "isPossibleMatch": true,
  "explanations": [
    "The photos have similar visual characteristics.",
    "The species, color, and markings are compatible.",
    "The selected locations are reasonably close.",
    "The found date is after the lost date and is compatible."
  ],
  "createdAt": "2026-09-25T12:00:01Z"
}
```

### Where data lives and how it changes

- Angular temporarily holds form values while the user edits them; validation and failed uploads do not clear them.
- The Python API is the source of truth after submission.
- Reports and match records are stored in local JSON files; images are stored in the local image folder.
- The API creates matches when a found report is submitted. The report detail page reloads them through `GET /api/reports/{report_id}/matches`.
- If the browser is refreshed or the processes restart, saved reports and images remain in the local data folders. No account-specific ownership is modeled.

## Matching Policy

### Visual score

Generate a normalized CLIP embedding for each report photo and compare the lost and found embeddings using cosine similarity. Convert the similarity into a bounded display score for the POC. This value is only a visual similarity signal: it is not the probability that two reports refer to the same animal. The exact display calibration must be checked during the first matching implementation; the UI must label it as similarity or match indication, not probability.

### Physical score

Calculate a transparent structured score from the report fields. Species agreement is required for a strong candidate. Color agreement and overlap in the markings/description terms contribute supporting points. Optional size agreement can add support when both reports provide it. The implementation should return the sub-reasons rather than hide them in a single opaque value.

### Geographic score

Look up both curated location records and calculate their distance using their fixed coordinates. Convert closer distance into a higher bounded score. The interface explains proximity in plain language rather than showing false precision.

### Date score

A found report dated before the lost report is incompatible and should not be surfaced as a possible match. For valid ordering, closer dates receive stronger support according to a simple documented rule. The exact decay bands should be verified against the demo data and kept in configuration.

### Combined indication

Use these named initial weights:

```text
visualWeight = 0.40
physicalWeight = 0.30
geographicWeight = 0.15
dateWeight = 0.15
```

The rationale is that visual similarity is the primary evidence, physical characteristics are a strong guard against appearance-only matches, and location and date provide meaningful contextual support. The weights are an interpretable starting policy, not statistical truth or calibrated confidence. The combined result is a `Possible match` indication, not a confidence claim or certainty that the animals are the same. Keep the weights in one configuration object so the build can adjust them after representative sample scenarios.

A possible match is surfaced only when the date is compatible and the combined indication reaches the initial configurable threshold. The threshold and date decay bands are implementation settings to verify during the build; they must not be presented as scientific certainty.

### Representative verification scenarios

The build should check at least these cases:

1. High visual similarity, compatible physical characteristics, nearby locations, and valid dates should surface a possible match.
2. High visual similarity with incompatible species or a found date before the lost date should not surface a possible match.
3. Moderate visual similarity with strong physical agreement and nearby location should show meaningful supporting contributions rather than being discarded solely because the photos differ.
4. Similar-looking reports from distant locations should show the geographic weakness clearly and should not be treated as equally strong.

## External Services and Dependencies

There are no required hosted external services or API keys.

- Angular and TypeScript: browser application dependencies. Docs: [Angular](https://angular.dev/), [TypeScript](https://www.typescriptlang.org/docs/).
- FastAPI and Uvicorn: local HTTP API and development server. Docs: [FastAPI](https://fastapi.tiangolo.com/), [Uvicorn](https://www.uvicorn.org/).
- Transformers and PyTorch: local CLIP model inference. Docs: [Transformers CLIP](https://huggingface.co/docs/transformers/model_doc/clip), [PyTorch](https://pytorch.org/docs/stable/index.html).
- Pillow: local image loading and preprocessing. Docs: [Pillow](https://pillow.readthedocs.io/en/stable/).
- Hugging Face model files: downloaded locally on first use from the selected model repository. No token is required for the public initial model; verify availability and download size during setup. Do not commit model files.

Ollama is intentionally not a dependency. It adds no clear benefit to deterministic image and contextual matching in this POC.

## Important Failure Modes

- **Missing or invalid required form data** -> Angular keeps all entered values, highlights only the affected fields, and shows a specific friendly message.
- **Photo upload or image-processing failure** -> Angular shows a non-technical retry message and preserves the rest of the form; the API does not create a partial report.
- **CLIP model unavailable or too slow to initialize** -> The API reports a clear local setup error and the build investigates the agreed lightweight CLIP fallback; it does not silently claim visual evidence that was not computed.
- **No compatible match** -> The report detail page shows `No possible matches yet` and explains that a future compatible found report may appear.
- **Missing or malformed local JSON data** -> The API creates a valid empty data file or returns a clear local setup error; it does not discard unrelated saved data.

## What Was Simplified and Why

- **Local JSON and image files** instead of a hosted database and object storage — the POC needs inspectable persistence, not concurrent production access.
- **Curated Coquimbo locations with fixed coordinates** instead of free-text geocoding and maps — this makes geographic evidence deterministic without an external API.
- **Matching when a found report is submitted** instead of a background job or continuously running matcher — it preserves the kernel while keeping behavior visible and easy to debug.
- **A small sample set** instead of a large search corpus — the demo only needs to prove that a relevant connection is surfaced.
- **Named weighted evidence** instead of an opaque model decision — the learner needs to understand why a match appeared, and the product must not claim certainty.
- **No Ollama or LLM** instead of adding conversational generation — an LLM does not improve the core visual/contextual comparison and would add another dependency.

## Decisions and Open Issues

### Learner-approved decisions

- Angular and TypeScript for the frontend, because they are familiar and support the desired responsive web experience.
- Python for matching, because the learner wants to understand image embeddings and contextual scoring.
- Two local processes communicating over HTTP, because the separation keeps the UI and matching logic independently inspectable.
- A local CLIP model, initially standard CLIP through established tooling, because the learning goal is meaningful visual similarity without hosted API keys.
- Local JSON and image folders, because the POC should be transparent, simple, and independent of external services.
- Curated Coquimbo sectors or communes with fixed coordinates, because geographic matching should be deterministic without a maps API.
- Visual/physical/geographic/date weights of 40/30/15/15, because visual evidence leads while no single signal should be proof. The weights must remain adjustable and be verified against sample scenarios.

### One useful uncertainty clarified

The learner wanted to understand how visual and contextual signals can work together without arbitrary or opaque AI behavior. We clarified that CLIP supplies one visual signal, while structured contextual scores remain separate and visible; the weighted policy is an interpretable starting point rather than a probability. Representative scenarios and matching tests will provide the build evidence for whether the initial policy behaves as intended.

### Open issues to verify during the build

- Confirm the compatible Angular, Node.js, Python, PyTorch, and Transformers versions on the local machine before installation.
- Verify the local CLIP model download size and CPU inference time. If impractical, investigate the lightweight CLIP fallback while preserving the same API and evidence contract.
- Choose the initial curated Coquimbo location list and document the source or rationale for its fixed coordinates.
- Calibrate the display conversion from raw cosine similarity to a bounded similarity indication without labeling it confidence.
- Choose and test the initial possible-match threshold and date-decay bands against the representative scenarios. These are adjustable implementation settings, not product promises.
